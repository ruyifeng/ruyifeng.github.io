The AI Reviewer Doesn't Know Your Codebase
The AI Reviewer Doesn't Know Your Codebase

Your team has been writing the guardrails for years. They’re called PR comments.

The review problem

A few weeks ago, a teammate almost merged a bug based on an authoritative-sounding PR review from Claude Code. The core issue: the AI assumed a canonical implementation, but we rely heavily on custom types. Claude suggested returning Future instead of nested async types. While correct for 99% of Scala codebases, it completely missed our error handling. Our project specifically requires FutureOr, a proprietary type combining async and typed error handling that isn’t in any public documentation Anthropic trained on.

This is the review problem nobody talks about. AI is good at writing code now. The bottleneck has shifted to review. Teams respond by adding humans to the loop: every AI-generated change gets a senior engineer’s eyes before it merges. That works until it doesn’t.

The naive fix is more human oversight: add a senior engineer to check every AI suggestion before it merges. That’s a lot of work, and it defeats the purpose. If I’m delegating review to AI, I don’t want to manually audit everything it outputs. What I actually want is for the AI to close the loop on itself: absorb the institutional knowledge your team has accumulated, and apply it automatically without anyone having to intervene.

You don’t fix that by adding more humans to the loop. You fix it by giving the reviewer what it’s missing.

The fix is to give the AI explicit rules about our codebase. The question is where those rules come from. The answer turned out to be sitting in our GitHub history: eight years of review comments where senior engineers told junior engineers exactly what this codebase requires. I mined those comments and turned them into a rules file the AI can actually use.

The training data you already have

Every senior engineer on your team has been teaching juniors the same lessons in PR threads for years. Use FutureOr, not raw Future. Batch your database queries. N+1 patterns are our most flagged performance issue.

That knowledge is in your GitHub history, structured: one comment per concern, dated, attributed, and free.

Until you do something about it, no AI reviewer can use it. Distill them into rules, then feed those rules to the AI.

The pipeline

The whole thing took a weekend.

    B --> C["Analyze\nCluster by\ntopic: 246 groups"]
    C --> D["Synthesize\nClaude → RFC 2119\n~180 rules"]

1. Pull the comments

I used the GitHub REST API to fetch all review comments from our main repo, from 2018 to today. Every comment includes text, author, file path, line number, PR number, and in-reply-to relationships.

Final pull: 16,687 review comments across 5,319 merged PRs.

2. Tag for filtering

Most review comments aren’t rules. They are LGTMs, questions, link-only replies, social acknowledgments. I tagged each comment along a few axes:

  • Reviewer (so I could weigh by seniority later if needed)
  • Era (early codebase comments are sometimes obsolete; we’ve changed frameworks and idioms since 2018, and a rule synthesized from 2019 can be wrong today)
  • File type (.scala, .sql, .conf, .proto, etc.)
  • Intent: nit / bug / architectural / question / LGTM

Tagging was mostly heuristic (length, regex, presence of code blocks), with Claude classifying intent for the ambiguous ones. Most LGTMs and substantive comments are obvious; regex handles them. Claude only sees the ambiguous cases, which keeps cost low.

3. Filter to high signal

I dropped LGTMs, link-only replies, and pure questions. That left 14,419 comments that express a preference, identify a bug, or propose a change.

4. Cluster by topic

Comments that all say the same thing should produce one rule, not 50. Sending 14,000 comments to an LLM produces noise proportional to your history’s repetition; you’d get near-duplicate rules for every paraphrase of the same concern. Clustering first means Claude synthesizes once per concept, not once per occurrence.

Within each file-type bucket, I grouped comments by semantic similarity into topic clusters.

246 topic clusters total. Each cluster is “all the times reviewers said roughly this same thing.”

For example, one cluster pulled every comment that flagged N+1 queries. Another collected every “don’t use ExecutionContext.global.”

5. Synthesize rules with Claude

For each cluster I gave Claude the comments and asked it to produce a rule in RFC 2119 format: MUST, MUST NOT, SHOULD, SHOULD NOT. RFC 2119 is the standard for normative language in technical specs. A rule saying “prefer FutureOr” gives a reviewer nothing to act on. A MUST gives it a threshold: flag this, no exceptions. Thresholds make output actionable; preferences don’t.

For each rule, I asked Claude to:

  • State the rule in one sentence
  • Note the rationale drawn from the comments
  • Flag whether it’s project-specific or generic Scala

6. Deduplicate, merge, order

After synthesis, several clusters produced the same rule from different angles. I merged duplicates, dropped rules that boiled down to “follow generic Scala style” (the model already knows those), and ordered the file: project-specific first, stack-specific second, generic style last.

Output: ~180 rules in a single file, covering error handling, database migrations, naming, and observability.

The guardrails that were already there

Project-specific rules

Use cases MUST return FutureOr[UseCase.Success, UseCase.Error].

This is the FutureOr rule. The one Claude got wrong. Generic Claude doesn’t know this type exists; it will suggest Future or Either. Both compile. Both are wrong. [Add one sentence: the first real PR where this caught something. One instance beats any general claim.]

In for-comprehensions, .toFutureOr MUST NOT be called on values already FutureOr — produces silent nesting.

The bug compiles, ships, and swallows errors without warning. Generic reviewers miss it.

Customer-facing API schemas MUST NOT use internal terminology (e.g., “subscription” -> “monitor”).

Our internal model has a type called subscription. Our customers see it as monitor. Using the wrong term in an external API is a real bug; we’ve caught it in review more than once.

Stack-specific gotchas

findByIds silently drops missing IDs; callers MUST use findByIdsOrdered (errors on missing) or explicitly check the result map.

A footgun specific to our jOOQ helper layer.

Partitioned-table indexes MUST be created on the parent with ON ONLY, then CONCURRENTLY on each partition, then attached.

The pattern comes from measuring lock duration on a 50M-row table. No model trained on Stack Overflow knows this is your team’s policy.

Non-obvious correctness rules

Database queries MUST be batched — not issued one-per-item in a loop; N+1 patterns are the single most-flagged performance issue.

“Avoid N+1” is generic advice. The parenthetical, “single most-flagged performance issue,” is empirical: I read every flagged comment to find that out. A reviewer that knows this is the #1 issue treats every loop as a suspect.

Metric dimensions MUST NOT include high-cardinality values (record IDs, user IDs); each unique combination creates a new series.

How I’m using it

Two modes, depending on whether you want interactive or automated review.

Interactive: Claude Code skill

I keep the rules file at the root of the repo and package it as a Claude Code skill with a steering section in SKILL.md so you can tune behavior per session:

  • skip style: drop the Scala style rules, focus on sections 1–3
  • correctness only: only flag MUST and MUST NOT violations
  • focus on <topic>: narrow scope to one section

I prompt with “do a peer review of the changes in the current branch” and Claude picks up the skill. Good for deep dives before a PR goes up, or for reviewing someone else’s branch with full context.

Automated: inject into a PR review bot

The rules file is tool-agnostic. Any bot that accepts a custom instructions file or system prompt can use it. The RFC 2119 format — one rule per sentence, explicit strength level — slots cleanly into a system prompt without reformatting.

A few integrations that work:

  • CodeRabbit: accepts a .coderabbit.yaml with custom review instructions per repo. Point it at the rules and it applies them to every PR automatically.
  • PR-Agent (CodiumAI): open source, supports a custom system prompt per repo via .pr_agent.toml. Drop the rules in and it runs on every PR open.
  • Cursor BugBot: pass the rules file as additional context in the bot configuration. Fires on PRs opened in Cursor.
  • GitHub Actions + Claude API: a workflow that triggers on pull_request, passes the diff and rules file to Claude, and posts a review comment. Fully custom, no third-party bot required.
  • Ellipsis: supports custom review guidelines per repo via a config file.

The interactive mode is where I started. The automated mode is the goal: every PR gets a codebase-aware review before a human ever looks at it.

The method is portable

These rules are specific to my codebase. The method works for any codebase with a few years of review history.

Every team has the same resource: years of human commentary that no general-purpose model has seen. The question is whether you’ve mined it.

PR comments are the obvious source, but the same shape works for:

  • Architectural decision records scattered across Confluence: “we chose X because Y, we explicitly rejected Z.” (A teammate suggested this in our internal thread, and he’s right.)
  • Incident postmortems: I turn corrective actions into MUST/MUST NOT rules.
  • Customer support transcripts: I turn recurring confusions into product-convention rules for a customer-facing AI.
  • Engineering Slack channels: engineers answer the same questions the same way for years.

LLMs are now good enough to handle the synthesis step; a year ago, this was a month-long ML project. I built this in a weekend.

What worked, what didn’t

What worked. Sections §1–§3 (project conventions, stack-specific gotchas, non-obvious correctness) are tight. On real PRs, the reviewer catches what our senior engineers catch, without requiring anyone to read the whole diff. False-positive rate is low; most flags are actionable.

What didn’t. Section §4 (Scala style and standard practices) is messier. Some rules are overstated MUSTs that should be SHOULDs. A few don’t match what we do today: they were correct in 2019 and the codebase has moved on. I’m pruning those and considering dropping §4 entirely; generic AI reviewers already handle style.

Open question: maintenance. Rules go stale as the codebase evolves. The natural answer is to automate it: a scheduled Claude agent runs the pipeline on a cron, diffs the output against the current file, and opens a PR with proposed additions and removals. New rules get a human review before merging; rules that haven’t appeared in recent comments get flagged for staleness. The pipeline is cheap enough to run quarterly, and with an AI cron the only manual step is approving the diff.

Try it on your repo

Human in the loop is not a bad idea. It’s the right answer to the wrong problem. The problem isn’t that AI needs a human watching it. It’s that the AI reviewer doesn’t know your domain. Your PR history does.
